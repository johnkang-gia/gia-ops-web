# 자료가 한 곳에 모이고, 한 곳에서 고치면 전체가 따라오는 구조

이 문서는 **설계**입니다. 지금 코드가 이렇다는 뜻이 아니라, 여기로 간다는 뜻입니다.
어디까지 됐는지는 각 절 끝에 적었습니다.

---

## 0. 지금 무엇이 문제인가 — 실측

세 가지가 각각 따로 새고 있습니다.

| 무엇 | 실측 |
|---|---|
| 표 | **55개**. 갈래에 등록된 적 없음 |
| 이름을 학생에 잇는 관문 | `resolveStudent` 를 부르는 파일 **5개**, 안 부르고 직접 대조하는 파일 **9개** |
| 사람이 가르친 규칙 | 표는 하나(`attendance_learning_rules`). 읽는 파일 **13개**, 그중 실제로 **해석에 쓰는** 파일 **6개** |
| 중복을 막는 열쇠 | 핵심 표 8개 중 **2개**에만 있음(`pickup_schedules`·`attendance_entries`) |
| 넣기·내리기 짝 | 여섯 갈래 중 **둘**만 짝이 맞음(픽업·업무) |

**규칙은 매번 멀쩡했고, 규칙을 안 거치는 자리가 매번 새로 생겼습니다.** 그 자리는 사고가
난 다음에야 발견됩니다.

## 1. 뼈대 — 자료 등기소

`src/lib/registry/dataKinds.ts` 한 파일에 **자료 종류마다 한 번씩** 적습니다.

```
종류      정식 표(모이는 한 곳)   딸린 표      중복 열쇠            넣기 → 내리기
학생      wr_students            9            id                   classAssign → (없음)
픽업      pickup_requests        7            source+source_ref    pickupIngest → pickupUndo
출결      attendance_entries     3            source+메시지+이름+상태  attendanceEntries → (없음)
셔틀      shuttle_assignments    5            날짜+배정             pickups → pickupUndo
재무      invoices              12            학생+학기+종류        invoices → cancel
업무      tasks                  5            (막지 않음·이유 적음)  pickupTask → pickupUndo
```

이 표가 **코드 안에** 있는 것이 요점입니다. 문서에만 있으면 코드와 곧 갈라집니다.

**빌드가 지킵니다.** `scripts/check-data-registry.mjs` 가 마이그레이션이 만든 표를 전부
훑어, 등기소에 없는 표가 있으면 빌드를 멈춥니다. 새 표를 만드는 **그 자리에서** 종류를
정하게 하는 것이 목적입니다 — 나중에 정하면 그 사이에 다른 화면들이 제각각 해석해서
씁니다.

> **된 것** — 등기소 55개 표 등록 완료, 검사기 빌드에 연결(20번째).

## 2. 들어오는 자리 — 분류 → 해석 → 중복 검사 → 저장

새 자료는 **네 걸음**을 반드시 거칩니다. 지금은 걸음마다 코드가 흩어져 있어 어떤 경로는
두 걸음만 밟고 저장됩니다.

```
① 분류    이 글은 픽업인가 결석인가 문의인가        pickupIngest 의 AI 판단
② 해석    이름 → 학생 번호. **규칙을 여기서 적용**   resolveStudent(+aliases)
③ 검사    이미 있는 자료인가                        중복 열쇠
④ 저장    정식 표 한 곳에                            apply 함수
```

### ②가 핵심입니다 — 규칙이 이름에 붙는다는 뜻

지금 `resolveStudent` 는 별칭을 **선택 인자**로 받습니다. 부르는 쪽이 안 넘기면 규칙이
그냥 안 붙고, 오류도 안 납니다. 「가르쳤는데 저기서는 안 되네」가 여기서 나옵니다.

바꿀 방향: **규칙을 안 넘기면 부를 수 없게** 합니다.

- 서버에서 부르는 자리는 `loadAliasIndex` 를 거친 관문 하나만 씁니다.
- 화면에서 부르는 자리도 같은 표를 읽어 넘깁니다.
- `scripts/check-student-match.mjs` 가 이미 「별칭 안 보는 코드」를 막고 있습니다.
  여기에 **「aliases 없이 resolveStudent 를 부르는 코드」**를 더합니다.

규칙이 이름에 붙으면, 새로 만든 화면이 이름을 쓰는 순간 그 규칙이 **자동으로** 따라옵니다.
화면이 규칙을 «적용하는» 것이 아니라, 이름을 해석하는 길이 하나뿐이라서 그렇게 됩니다.

### ③은 DB 가 지켜야 합니다

코드로만 막으면 두 사람이 동시에 누를 때 뚫립니다. 중복 열쇠는 **등기소에 적힌 것과 같은
칸으로 DB 에 unique 색인**을 겁니다. 지금 빠진 곳:

- `shuttle_boardings (service_date, assignment_id)`
- `pickup_requests (source, source_ref)`

> **아직** — ②의 강제와 ③의 색인은 다음 단계입니다.

## 3. 나가는 자리 — 넣었으면 내린다

넣는 쪽은 대개 한 함수가 여러 표를 함께 씁니다. **내리는 쪽은 화면마다 따로 만들어졌습니다.**
그래서 세 표에 자국이 남았는데 한 표만 고치고, 나머지를 읽는 화면에서 그 자료가 계속
살아 있습니다. 강하라가 그랬습니다.

규칙: **화면은 표를 직접 고치지 않습니다.** 갈래의 apply/undo 함수만 부릅니다.

지금 짝이 없는 자리(등기소의 `gap` 에 그대로 적혀 있습니다):

- 출결 — 내리는 짝 함수 없음
- 재무 — 청구서를 취소해도 `cash_receipts` 가 안 내려감
- 학생 — 지우는 길 없음(**이건 일부러 그렇습니다**. 지난 청구·출결이 함께 사라지면 안 됩니다)
- 픽업 — 상태를 바꾸는 7곳 중 2곳만 undo 를 거침

> **된 것** — 짝이 없는 사실을 숨기지 않고 등기소에 적어 뒀습니다(`openGaps()`).
> **아직** — 출결·재무의 undo 함수.

## 4. 왜 한꺼번에 안 바꾸나

55개 표, 화면 93개, 읽는 자리 700곳입니다. 한 번에 갈아엎으면 **무엇이 깨졌는지 알 수 없는
상태**가 며칠 갑니다. 이 앱은 매일 아침 137명의 하원을 정하는 데 쓰입니다.

그래서 순서를 이렇게 둡니다.

1. **뼈대와 검사기 먼저** — 새로 생기는 자리가 규칙 밖으로 못 나가게 (지금 한 것)
2. **관문 강제** — 이름 해석이 규칙을 반드시 거치게
3. **DB 중복 색인** — 코드가 아니라 표가 막게
4. **짝 없는 undo 채우기** — 출결·재무
5. **직접 대조하는 9개 파일을 관문으로** — 하나씩, 갈래별로

각 단계는 그 자체로 쓸모가 있고, 중간에 멈춰도 앞 단계가 손해가 되지 않습니다. 이것이
「한 번에 다 바꾸기」보다 느려 보이지만, 실제로는 **되돌릴 일이 없어서** 빠릅니다.

## 5. 이 구조가 실제로 막는 것

이번 주에 난 일들이 각각 어디서 걸렸을지:

| 실제로 난 일 | 어느 단계가 막나 |
|---|---|
| 김재이·심재이·유재이가 다 픽업 | ② 관문 강제 (이름으로 고르는 길이 없어짐) |
| 오늘 픽업에 같은 아이 3줄 | ③ 중복 열쇠 (`source+source_ref`) |
| 강하라가 대시보드에 계속 남음 | ③ 넣기·내리기 짝 |
| 토들 채널에서 생일이 빠짐 | ② 관문 하나 (옮기는 자리가 사라짐) |
| 마이그레이션 두 판 실패를 일주일 몰랐음 | (다른 문제 — 실패를 앱 안에 띄우는 것) |
