# 업무 메뉴 전체 점검 — 2026-09-14

재무를 뺀 학교 업무 전체가 지나가는 자리(업무 메뉴)를 코드와 **라이브 자료 양쪽으로** 재어
보고 정리한 것입니다.

**두 번째 판입니다.** 첫 판에서 토들과 구글챗을 「같은 것이 두 번 들어오는 중복」으로 보고
합치자고 적었는데, 그건 틀렸습니다. 구글챗은 **토들 수집이 화면 긁기라서 놓칠 수 있기에
일부러 하나 더 둔 보험**입니다(§0-3①). 그 전제로 §1~3을 다시 썼습니다.

### 0-3. 그리고 이것이 이번 점검에서 가장 중요한 세 줄입니다

**① 토들과 구글챗은 중복이 아니라 이중 확인입니다. 그런데 서로를 못 찾습니다.**

먼저 두 창구의 역할을 정확히 적습니다. 이것을 잘못 알면 아래 제안이 전부 어긋납니다.

```
학부모 ──(토들)──▶ 행정직원        ← 문의가 전부 들어오는 창구
                      │
                      ├─(구글챗 직원방)─▶ 「누가 오늘 결석」  ← 담임·행정이 다시 올림
                      │
토들 수집은 **API가 아니라 화면 긁기**입니다. 놓치는 건이 있을 수 있어
구글챗을 **보험**으로 하나 더 둔 구조입니다.
```

**보험은 실제로 값을 하고 있습니다.** 구글챗에서 온 결석 판정 45건 중 같은 학생·같은 날의
토들 줄이 있는 것은 **10건(22%)** 뿐입니다. 나머지 35건은 구글챗에만 있습니다. 이유는
둘 중 하나인데 지금은 **어느 쪽인지 화면에서 알 수 없습니다.**

- 토들 수집이 그 글을 놓쳤다 → 보험이 건진 것. 수집기를 고쳐야 합니다.
- 토들 줄은 있는데 **학생이 안 정해져 있어**(525건 중 211건) 맞출 수 없었다 → 맞추기 문제입니다.

그런데 두 표를 잇는 열쇠가 없습니다. `pickup_requests.source_ref`(토들 메시지 번호
`418476671973301296`)와 `attendance_entries.source_message_id`(우리가 만든 UUID)의
**겹치는 값이 0개**입니다. 그래서

- 인박스에서 「확정」한 연락과 출결내역에서 「등록」한 연락이 같은 문장에서 나왔어도 서로 모르고,
- **보험이 맞았는지 틀렸는지 아무도 볼 수 없습니다.** 두 창구가 같은 말을 했는지 다른 말을
  했는지가 화면에 안 나타나면, 보험을 들어 둔 값이 하나도 안 나옵니다.

**② 확정한 결석이 출석부에 안 들어갑니다.**

`attendance_entries` 에 「등록 + 결석」이 **34건**인데 `attendance_records` 의 결석은
**7건**입니다. 27건이 출석부에 없습니다. 날짜로도 드러납니다 — entries 는 8/13~9/21,
records 는 **9/4~9/11 뿐**입니다. 9월 4일 이전의 결석은 출석부에 한 줄도 없습니다.

거기에 `school_days` 가 **0건**이라, 출석률 식
`(수업일수 − 결석일수) ÷ 수업일수` 의 **분모가 없습니다.** 출석 화면은 오류를 내지
않고 그냥 아무 숫자도 못 냅니다.

**③ 업무보드의 중심(`tasks` 41건)이 실제 업무량(`pickup_requests` 525건)의 8%입니다.**

칸반·달력·보고서·보관함·휴지통이 전부 41건짜리 `tasks` 를 돌보고 있고, 학교에 실제로
들어오는 525건은 인박스 칸 안에 접혀 있습니다. 그중 **292건(56%)이 아직 확인대기**이고,
그 숫자는 화면 어디에도 안 뜹니다.

## 1. 업무 메뉴 구성 — 무엇이 불편한가

### 1-1. 탭이 두 겹이고, 같은 것이 두 번 떴습니다

바깥 탭 4개 안에 인박스 탭 4개가 또 있었습니다. 그중 **「🚸 출결알림」은 바로 아래 칸
(구글챗)이 이미 보여주는 방**이었습니다 — 창을 여러 개 안 띄우려고 만든 자리가 한 화면
안에서 같은 내용을 두 번 띄우는 자리가 됐습니다. 이 탭은 이번에 내렸습니다(v0.575.0).

남은 두 겹도 문제입니다. 어제 온 결석 연락을 찾으려면 업무 보드 → 인박스 → 출결내역 →
날짜를 거쳐야 하는데, 같은 아이 이야기가 [학부모 문의] 탭에도 있습니다. §0-3① 때문에
두 탭의 상태가 서로 다릅니다.

### 제안 — 탭 넷을 셋으로, 안쪽 탭은 둘만

```
업무 보드 (/work)   ← 오늘 해야 하는 것. 여기서 다 처리합니다(§3)
연락 찾기 (/work/search) ← 지난 연락 검색 + 기간 + 종류. 지금 메뉴에서 내려가 있는 화면
보고서 (/work/report)    ← 연락·출결·업무 셋 다 세도록 넓힘
보관함                    ← 지난 업무 · 휴지통 (그대로)
```

**하원수단**은 화면을 남기되 탭에서 내려 「학교 → 학생」 아래로 옮깁니다. 10건짜리를 매일
보는 줄에 두는 대신, 보드에서 하원 관련 연락을 처리할 때 **그 자리에서** 하원수단을 고칠
수 있게 합니다. 번거로워서 안 쓰이는 것이지 필요 없는 기능이 아닙니다.

### 2-1. 없앨 것 (줄이 0이고, 대신할 자리가 있는 것)

| 업무 첨부 | — | `task_attachments` 0 | **없앱니다** |
| 날짜 알림 | — | `day_reminders` 0 | **없앱니다.** 업무 달력이 같은 일을 합니다 |
| 공지 배너 `NoticeBanner` | 367줄 | `work_notices` 0 | **자리를 옮깁니다** — 아래 참고 |

공지 배너만 성격이 다릅니다. 「안 쓴다」가 아니라 **「만드는 길이 없다」**에 가깝습니다 —
공지를 쓰는 단추가 보드 안쪽에 있어서 아무도 못 찾습니다. 지우는 대신 보드 맨 위 고정
줄로 옮기고, 쓸 자리가 분명해진 뒤에도 0건이면 그때 지웁니다.

### 2-2. 합치지 **않을** 것 — 토들과 구글챗

앞서 「두 인박스를 하나로」라고 적었던 것은 **틀렸습니다.** 두 창구는 성격이 다릅니다.

| | 토들 | 구글챗 |
|---|---|---|
| 누가 씁니까 | 학부모 | 담임·행정직원 |
| 무엇이 옵니까 | 문의 전부(284건 문의 · 78건 픽업 · 163건 기타) | 「오늘 누가 결석」만 |
| 어떻게 받습니까 | **화면 긁기**(놓칠 수 있음) | 미러링 |
| 역할 | 원본 | **보험** |

**둘을 한 목록으로 섞으면 보험이 사라집니다.** 섞는 순간 「한쪽에만 있다」가 안 보이게
되고, 그게 바로 수집기가 놓친 건을 찾는 유일한 신호입니다.

### 2-3. 대신 합칠 것 — **두 창구를 맞대어 보는 자리**

합칠 것은 목록이 아니라 **판정**입니다. 같은 학생·같은 날에 대해 두 창구가 무엇을
말했는지를 한 줄에 나란히 둡니다.

```
정레인 (G2C) · 9월 14일 · 결석
  토들   09:12  「감기로 오늘 결석합니다」            ✅ 읽음
  구글챗 09:40  「@행정실 정레인 오늘 결석」          ✅ 읽음
  → 양쪽 확인됨
```

```
임주한 (G4A) · 9월 12일 · 결석
  토들   —                                          ⚠ 없음
  구글챗 08:55  「임주한 오늘 못 옵니다」             ✅ 읽음
  → 구글챗에만 있습니다 — 토들에서 놓쳤을 수 있습니다
```

이 한 화면이 하는 일이 셋입니다.

1. **보험이 건진 건을 눈에 보이게 합니다.** 지금 45건 중 35건이 여기 뜹니다.
2. **수집기를 고칠 단서가 됩니다.** 「구글챗에만」이 계속 나오는 학부모·채널이 있으면
   그 채널을 수집기가 못 읽고 있는 것입니다.
3. **한쪽만 처리하고 끝나는 일이 없어집니다.** 지금은 토들 쪽에서 처리해도 구글챗 쪽 줄이
   대기로 남고, 그 반대도 같습니다.

**한쪽에만 있어도 처리는 됩니다.** 「양쪽 확인」을 조건으로 걸면 안 됩니다 — 학부모가
구글챗에 글을 쓸 일은 없고, 담임이 모든 문의를 구글챗에 다시 올리지도 않습니다.
양쪽 확인은 **더 믿을 만하다는 표시**이지 처리의 조건이 아닙니다.

### 2-4. 나머지 정리

- **구글챗 화면 둘 → 하나.** `GoogleChatRooms`(633줄)와 `GoogleChatMirrorPanel`(265줄)이
  같은 구글챗을 각자 보여줬습니다. 미러 패널을 내렸습니다.
- **보고서는 없애지 말고 넓힙니다.** 지금은 `tasks` 41건만 셉니다. 학교가 실제로 한 일은
  연락 525건을 받고 그중 292건을 아직 못 본 것입니다. **연락 처리량·미처리 적체·두 창구
  일치율**을 함께 세면 그때 쓰이기 시작합니다.
- **보관함도 연락을 받습니다.** 지금은 `tasks` 만 담습니다. 무시 처리한 연락 206건
  (픽업 177 + 출결 29)은 어디에도 모이지 않아 잘못 무시한 것을 되찾을 길이 없습니다.

## 3. 업무보드 — 페이지를 옮기지 않고 여기서 끝냅니다

### 3-1. 확인대기 292건의 진짜 이유

처음에는 「숫자가 안 보여서」라고 적었는데, 그건 절반입니다. 실제 이유는 **처리하려면 다른
페이지로 가야 하기 때문**입니다. 옮겨가야 하는 일은 대개 안 합니다 — 그래서 292건(56%)이
쌓였습니다.

같은 원인이 이 저장소에서 이미 두 번 확인됐습니다.

- 픽업을 잘못 읽은 것을 되돌리는 자리가 **하원 체크표에만** 있어서, 문의 목록에서 잘못을
  발견한 사람은 화면을 옮겨야 했습니다.
- 하원수단을 넣는 자리가 **학생 프로필 안**에 있어서, 「나중에 하자」가 됐고 지금 10건입니다.

### 3-2. 원칙 — 보드 밖으로 나가지 않습니다

연락 한 줄에서 할 수 있어야 하는 일 전부:

| 무엇 | 지금 어디 | 바뀔 곳 |
|---|---|---|
| 결석 · 지각 · 조퇴 처리 | 인박스 탭 / 출석부 | **그 줄의 팝업** |
| 픽업 · 탑승 처리 | 하원 체크표 | **그 줄의 팝업** |
| 잘못 읽은 것 되돌리기 | 하원 체크표 | **그 줄의 팝업**(v0.575.0에서 옮겼습니다) |
| 하원수단 고치기 | 학생 프로필 · 하원수단 화면 | **그 줄의 팝업** |
| 누구인지 정하기 | 픽업 인박스 | **그 줄의 팝업** |
| 업무로 올리기 | 이미 됨 | 그대로 |
| 토들에서 답하기 | 이미 됨 | 그대로 |
| 두 창구 대조 보기 | **없음** | **그 줄의 팝업**(§2-3) |

**목록은 읽는 자리, 팝업은 손대는 자리.** 목록 한 줄에 누를 것이 다섯이면 훑어보기가 안
되고, 원문을 안 읽은 채 누르게 됩니다. 이번에 문의 목록을 그렇게 바꿨습니다 — 목록은
`이름 · 분류 · 처리사항 · 내용 · 시각` 만, 나머지는 이름을 눌러 나오는 팝업으로.

### 3-3. 화면 모양

```
┌─────────────────────────────────────────────────────────────┐
│ 봐야 할 것 404 · 오늘 결석 7 · 오늘 픽업 12 · 기한 지남 3      │  ← 맨 위 한 줄
├───────────────────────┬─────────────────────────────────────┤
│  📥 인박스             │  오늘                                │

```

- 맨 위 숫자는 지금 **화면 어디에도 없습니다.** 확인대기 292 + 확인필요 88 + 예정 24 = 404.
- 줄의 `⚙` 는 앱이 한 일, `양쪽✓` 는 두 창구가 같은 말을 했다는 표시입니다.
- 구글챗 칸은 **오른쪽에 그대로 둡니다.** 보험이니까 눈에 보여야 합니다.

### 3-4. 상태값을 네 칸으로 줄입니다

지금 표마다 상태값이 다릅니다 — `확인대기·확정·무시` / `확인필요·등록·무시` /
`예정·진행중·완료`. 사람이 셋을 외울 이유가 없습니다. 화면은 **봐야 할 것 / 오늘 /
기다림 / 끝** 네 칸으로만 말하고, 표별 상태는 안에서 옮깁니다.

### 3-5. 「이 화면 하나만」이 되려면 더 들어와야 하는 것

- **오늘 하원 체크표 요약** — 지금은 셔틀 메뉴에만 있습니다. 오후 3시 반부터 행정실이
  실제로 보는 것은 이 화면입니다.
- **오늘 결석·지각 명단** — 출석부에서 읽어야 하는데 출석부가 8건뿐이라 지금은 못 읽습니다
  (§4를 고쳐야 나옵니다).
- **묵은 연락** — 확인대기 292건 중 8월 것이 남아 있습니다. 3일 넘은 줄은 빨갛게.

## 4. 데이터 구조 — 여러 갈래에서 들어와 한 곳으로

### 4-1. 지금의 모양

```
토들 ─┬─▶ pickup_requests (525)  ──▶ tasks (9건만)
      └─▶ attendance_entries ─┐
구글챗 ──▶ attendance_entries ─┴─▶ attendance_records (8)
                                └─▶ shuttle_boardings
```

- `pickup_requests` 와 `attendance_entries` 는 **열쇠가 안 맞아 서로를 못 찾습니다**(겹침 0).
- 구글챗은 `pickup_requests` 에 아예 안 들어갑니다.
- `attendance_entries` → `attendance_records` 가 **34 → 7** 로 새고 있습니다.

`src/lib/registry/dataKinds.ts` 의 `gap` 이 이미 같은 말을 하고 있습니다.

> 출결: 「출결을 내리는 짝 함수가 없습니다.」
> 픽업: 「pickup_requests 의 상태를 바꾸는 자리 7곳 중 2곳만 undo 를 거칩니다.」
> 셔틀: 「shuttle_boardings 에 (service_date, assignment_id) unique 색인이 없습니다.」

### 4-2. 제안 — 세 층

```
① 받은 것 (communications)   원문. 절대 고치지 않음 · 창구별로 **따로 남습니다**
   토들 · 구글챗 · 전화 · 직접입력
   열쇠 = (source, source_ref)        ← 그 창구가 준 번호를 그대로

② 읽은 것 (intents)          한 메시지에서 여러 건이 나올 수 있음
   누구(student_id) · 무엇(결석/지각/조퇴/픽업/탑승/문의/업무)
   · 언제(date_from~date_to) · 누가 판정(자동/사람) · 상태(봐야 할 것/처리/무시)
   · 왜 그렇게 읽었나(why)
   · **근거가 된 ① 줄들**(하나가 아닙니다 — 토들 + 구글챗 둘 다일 수 있습니다)

③ 일어난 것 (facts)          정본. 모든 화면이 읽는 곳
   attendance_records · shuttle_boardings · tasks · student_dismissal_plans
   ← 각 줄이 자기를 만든 ②의 번호(intent_id)를 들고 있음
```

**왜 이 모양인가**

- **①은 창구별로 따로 남습니다.** 토들 줄과 구글챗 줄을 한 줄로 합쳐 버리면 「한쪽에만
  있다」가 사라지고, 그게 바로 수집기가 놓친 건을 찾는 유일한 신호입니다(§2-2).
  원문을 고치는 것도 안 됩니다 — 「그때 학부모가 뭐라고 했더라」를 물어볼 곳이 사라집니다.
- **②는 하나입니다.** 같은 학생·같은 날·같은 종류면 **판정은 한 줄**이고, 그 한 줄이 근거가
  된 ① 줄을 여럿 답니다. 이것이 §2-3의 대조 화면이 그대로 서는 자리입니다.

  ```
  intent  정레인 · 9/14 · 결석 · 확정
     ├── 근거  토들   09:12  「감기로 오늘 결석합니다」
     └── 근거  구글챗 09:40  「@행정실 정레인 오늘 결석」   → 양쪽 확인됨
  ```

  지금 ②가 두 벌(`pickup_requests` · `attendance_entries`)인 것이 §0-3①의 원인 전부입니다.
  하나면 어느 화면에서 처리하든 상태가 하나이고, **보험이 맞았는지가 저절로 보입니다.**
- **③은 ②를 가리킵니다.** 되돌릴 때 무엇을 지울지 찾을 수 있고, 화면이 「이건 9월 3일
  토들 연락에서 자동으로 들어온 결석입니다」라고 말할 수 있습니다. 지금 `attendance_records`
  에는 `source` 글자만 있어서 어느 연락에서 왔는지 모릅니다.
- **②→③ 은 갈래마다 apply/undo 한 짝만** 씁니다. `attendanceApply.ts` 가 이미 그 모양이고,
  주석에 왜 그래야 하는지까지 적혀 있습니다. 나머지 갈래에 같은 것을 둡니다.

### 4-2-1. 두 창구를 무엇으로 맞춥니까

**이름으로는 못 맞춥니다.** 실제로 해 봤습니다 — 구글챗 줄의 이름이
「마야(Maya Amelia Dowding)」·「강하늘(Skye (Haneul) Kang)」처럼 적혀 있어서, 글자로 맞추면
45건 중 4건만 짝이 잡힙니다. **학생 번호로 맞추면 10건**입니다. 김재이가 셋인 학교에서
이름으로 맞추는 것은 어차피 안 됩니다(CLAUDE.md 2-4).

맞추는 열쇠는 **(student_id, 날짜, 종류)** 하나입니다. 그래서 토들 줄의
`student_id` 가 비어 있는 **211건(40%)** 을 채우는 일이 대조의 전제 조건입니다 - 번호가
없으면 그 줄은 어느 판정에도 못 붙고, 화면에는 「한쪽에만 있음」으로 잘못 뜹니다.

### 4-3. 한 번에 갈아엎지 않습니다 — 순서

**1단계 — 두 창구를 (번호·날짜·종류)로 맞대어 봅니다.**
표를 안 고치고 뷰 하나(`attendance_cross_check`)만 만듭니다. 지금 당장 나오는 것:
「양쪽 확인 10건 / 구글챗에만 35건 / 토들에만 N건」. 이 뷰가 §2-3 화면이 되고, 동시에
**토들 수집기가 얼마나 놓치는지**를 처음으로 숫자로 보게 해 줍니다.

**2단계 — 토들 줄의 학생 번호 211건을 채웁니다.**
1단계 뷰가 「한쪽에만」으로 잘못 세는 것을 걷어내는 일입니다. 토들 채널↔학생 연결
(`toddle_channel_students` 85건)을 넓히면 대부분 자동으로 붙습니다.

**3단계 — 화면이 읽는 곳을 뷰 하나로.**
`work_inbox` 뷰를 만들어 두 표를 한 목록으로 냅니다(화면은 창구를 여전히 구분해 보여줍니다 -
합치는 것은 **판정**이지 목록이 아닙니다). 화면은 표를 직접 안 읽습니다.
**표를 합치기 전에 화면부터 하나로** 만드는 것이 요점입니다 — 화면이 하나가 되면 표를
합칠 때 고칠 곳이 한 군데입니다.

**4단계 — ③으로 가는 길 채우기.**
결석만 있는 자동 반영을 픽업·하원수단·업무까지 넓히고, `intent_id` 를 붙입니다.
동시에 `attendance_records` 에 빠진 27건을 백필하고 `school_days` 를 학사일정에서 만듭니다.

**5단계 — 그 다음에야 ②를 하나의 표로 합칩니다.** ①은 창구별로 그대로 둡니다.

### 4-4. 검사로 지킵니다

기억으로는 안 지켜집니다(CLAUDE.md 서두). 빌드 게이트 **27호**를 답니다.

- 화면·API 가 `pickup_requests` · `attendance_entries` 를 **직접 update** 하는 자리를 막고
  apply/undo 만 쓰게 합니다. 지금 그런 자리가 픽업만 7곳입니다.
- 면제는 같은 줄에 `// inbox-write-ok: 이유`.

그리고 **적체 숫자를 개발자 화면에 상시로** 띄웁니다. 이 셋이 이 앱이 실제로 쓰이는지의
척도입니다.

| 지표 | 지금 | 뜻 |
|---|---:|---|
| 확인대기 연락 | 292 | 아무도 안 본 학부모 연락 |
| 학생이 안 정해진 연락 | 211 | 누구 이야기인지 모르는 채 쌓인 것 |
| 등록했는데 출석부에 없는 결석 | 27 | ②→③ 이 새는 양 |
| **구글챗에만 있는 결석** | **35 / 45** | **토들 수집기가 놓치는 양.** 보험이 건지고 있는 만큼입니다 |

## 5. 더 있으면 좋을 것

### 이용자(행정직원) 입장

1. **맨 위 한 줄 숫자.** 봐야 할 것 404 · 오늘 결석 · 오늘 픽업 · 기한 지난 업무.
   지금은 이 숫자를 아는 사람이 없습니다.
2. **한 줄 처리 + 한 번 되돌리기.** 되돌리기가 지금은 결석에만 있습니다. 잘못 누른 픽업·
   탑승은 어디를 지워야 하는지 매번 다시 찾아야 합니다.
3. **묵은 연락 재촉.** 3일 넘은 확인대기는 빨갛게, 7일 넘은 것은 맨 위로.
4. **누가 답했는지 목록에서 바로.** `replied_by` · `answered_by` 칸은 이미 있는데 목록에
   안 뜹니다. 두 사람이 같은 학부모에게 두 번 답하는 일이 막힙니다.
5. **학생 한 명 타임라인.** 그 아이의 연락·출결·픽업·업무를 시간순 한 줄로.
   재무의 통장식 화면(`/finance/monthly`)과 같은 모양입니다. 상담 때 이 화면 하나면 됩니다.
6. **연락 검색을 메뉴로.** 8월 연락을 찾을 길이 지금 없습니다.
7. **출석률이 나오게.** `school_days` 0건을 학사일정에서 자동으로 채웁니다.
8. **주간 한 장.** 이번 주 결석·픽업·미처리를 A4 한 장으로. 회의에서 그대로 씁니다.

### 개발자 입장

1. **빌드 게이트 27호** — 인박스 표 직접 쓰기 금지(§4-4).
2. **`work_inbox` 뷰** — 화면 여러 개가 같은 답을 하게 하는 가장 싼 방법입니다.
3. **적체 지표 상시 표시** — §4-4 표 셋.
4. **1,000줄 넘는 컴포넌트 둘을 합치면 저절로 줄어듭니다.** ParentInquiryPanel 1,142 +
   AttendanceDigestPanel 1,136 은 같은 일을 두 벌로 하고 있습니다. 뷰 하나 위에 목록
   하나면 400줄 안쪽입니다.
5. **되돌린 기록을 남깁니다.** 지금 누가 무엇을 되돌렸는지가 안 남아서, 사라진 줄을
   설명할 수 없습니다.
6. **`shuttle_boardings` 에 unique 색인** — 두 사람이 동시에 누르면 두 줄이 생깁니다
   (dataKinds 의 gap 에 이미 적혀 있음).
7. **인박스 목록에 페이지.** 지금 보드가 구글챗 400건을 한 번에 읽습니다. 525건이
   3,000건이 되는 데 한 학기면 됩니다.
